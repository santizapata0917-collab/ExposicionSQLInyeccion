01 · Concepto

¿Qué es la inyección SQL?

Es una vulnerabilidad que aparece cuando una entrada controlada por el usuario puede alterar la estructura de una consulta SQL.

⌨

Entrada

Una persona escribe en un formulario, buscador o parámetro de URL.

⟨/⟩

Consulta insegura

El programa mezcla la entrada con el código SQL sin separar datos e instrucciones.

▤

Base de datos

La consulta puede hacer algo distinto de lo que el desarrollador pretendía.

Idea clave: el problema no son simplemente los caracteres especiales. El problema es permitir que los datos se interpreten como código SQL.
02 · Recorrido del ataque

¿Cómo puede ocurrir?

Una sola consulta construida incorrectamente puede abrir una vía de acceso a información que no debería exponerse.

PASO 01

Usuario

Introduce un dato en un formulario o buscador.

PASO 02

Vista Django

La aplicación construye una consulta SQL insegura.

PASO 03

Motor SQL

La base de datos procesa la consulta recibida.

PASO 04

Consecuencia

Podrían consultarse, alterarse o eliminarse datos según los permisos.

Importante: la explotación real depende de cómo esté escrita la consulta, del motor de base de datos y de los permisos de la conexión.
03 · Causas

¿Qué vulnerabilidades lo permiten?

No tienen que estar presentes todas. La construcción insegura de una consulta puede ser suficiente; otros fallos aumentan el impacto.

⌘

Concatenación directa

Unir entradas del usuario al texto SQL mediante f-strings, concatenación o interpolación.

Causa directa
▤

SQL sin procesar mal usado

Usar cursor.execute(), raw() o RawSQL sin parametrizar correctamente.

Riesgo directo
✓

Validación insuficiente

No comprobar tipos, formato o límites. La validación ayuda, pero no sustituye la parametrización.

Debilidad adicional
⚿

Permisos excesivos y errores

Una cuenta de base de datos demasiado privilegiada o errores SQL visibles pueden agravar el impacto.

Aumenta el impacto
04 · Ejemplo de código

Una consulta vulnerable

Imagina una función que busca usuarios por correo electrónico. Observa cómo se inserta directamente la entrada en la consulta.

views.py · Ejemplo inseguroNo usar en producción
from django.db import connection

def buscar_usuario(correo):
    consulta = (
        "SELECT * FROM usuarios_usuario "
        f"WHERE correo = '{correo}'"
    )

    with connection.cursor() as cursor:
        cursor.execute(consulta)
        return cursor.fetchall()

¿Qué está mal?

La f-string inserta correo dentro del texto SQL. La entrada puede alterar la estructura de la consulta.

¿Qué debemos recordar?

Una entrada no confiable debe seguir siendo un valor, nunca convertirse en parte del código SQL.

Ejemplo conceptual para estudiar el fallo. Las pruebas de seguridad deben realizarse únicamente en sistemas propios o autorizados.

05 · Demostración didáctica

¿Por qué importa separar código y datos?

Esta demostración local ilustra el concepto sin conectarse a ninguna base de datos ni ejecutar SQL.

Entrada normal. En una consulta parametrizada, se trata como un valor de búsqueda.
Construcción insegura

La entrada se concatena al SQL. El texto podría cambiar la consulta si el código está mal diseñado.

Consulta parametrizada

La estructura SQL se mantiene separada del valor. Es la defensa recomendada.

La demostración es solo educativa: no ejecuta consultas, no prueba servidores y no determina por sí sola si una aplicación real es vulnerable.
06 · Prevención

La solución segura en Django

En la mayoría de los casos, el ORM es la opción más sencilla. Si necesitas SQL directo, usa parámetros en lugar de interpolar valores.

Recomendado

Usar el ORM

Consulta con Django
def buscar_usuario(correo):
    return Usuario.objects.filter(
        correo=correo
    )
  • Django gestiona los valores de la consulta.
  • El código es legible y fácil de mantener.
  • Usuario debe ser el modelo real de tu proyecto.
También válido

SQL parametrizado

Consulta SQL directa
with connection.cursor() as cursor:
    cursor.execute(
        "SELECT * FROM usuarios_usuario "
        "WHERE correo = %s",
        [correo]
    )
    usuarios = cursor.fetchall()
  • El marcador %s representa un parámetro.
  • El controlador procesa el valor por separado.
  • No uses f-strings ni concatenación para ese valor.
Regla de oro: parametrizar consultas. Validar entradas y restringir permisos son capas adicionales de defensa, no sustitutos de esa regla.
07 · Impacto

¿Qué consecuencias puede tener?

El daño posible depende de la consulta vulnerable, los permisos de la cuenta y las defensas de la aplicación.

◉

Confidencialidad

Exposición de información personal, registros internos u otros datos sensibles.

✎

Integridad

Modificación o eliminación de registros si la consulta y los permisos lo permiten.

◴

Disponibilidad

Interrupción de operaciones o consumo excesivo de recursos en ciertos escenarios.

Defensa en profundidad: el mínimo privilegio limita el daño potencial, incluso si se descubre un fallo en el código.
08 · Buenas prácticas

Lista de verificación para desarrolladores

Antes de desplegar una aplicación Django, revisa estos controles.

En el código

  • Priorizar el ORM de Django.
  • Parametrizar todas las consultas SQL directas.
  • Evitar concatenar datos no confiables.
  • Validar tipos, formatos y límites en el servidor.
  • Revisar cuidadosamente raw() y RawSQL.

En la infraestructura

  • Aplicar mínimo privilegio a la cuenta de base de datos.
  • No mostrar errores técnicos detallados al usuario.
  • Mantener Django y sus dependencias actualizados.
  • Probar casos inesperados con tests automatizados.
  • Revisar registros y corregir hallazgos de seguridad.
09 · Cierre

La seguridad empieza en el código

Django proporciona herramientas para desarrollar de forma segura, pero el resultado depende de cómo las utilizamos.

Comprender

02

Prevenir

03

Verificar

Revisar el código y probar el comportamiento de forma autorizada.
